Direct vs. Guide

A staged pilot of the balash-guide-experiment-v2 protocol: does separating engineering-objective selection from implementation change what gets built, as a small task manager absorbs four unforeseen product changes?

Headline

The result is a genuine split, not a win for either side. An independent, blind, adversarial reviewer — shown only anonymized final code, no process history — preferred Guide's tests as a safety net for future change, but said it would rather have inherited Direct's production code as the base to build on.

Guide's process produced stronger structural guarantees (proof-carrying tests that a rule is enforced in exactly one place; a backend-equivalence suite that auto-enrolls new backends) at the cost of real unrequested complexity (an agent registry nobody asked for, dead code, duplicated adapters). Direct's process produced leaner code that matched each requirement's literal scope — and shipped three real, untested invariant violations that the blind reviewer found by adversarial probing, not by reading the test suite.

Method

What actually ran

Two isolated git repositories, each built from the same four product requirements delivered one at a time (no future stage visible to either condition). Both used the same implementation model. Direct received each requirement verbatim and built it. Guide was played by the orchestrating session itself: one discovery question per stage answered from a fixed non-technical-owner oracle, one narrow engineering objective chosen and written to durable state, implementation delegated to a fresh Worker subagent, evidence evaluated before moving on.

After every stage, before committing, the orchestrator independently re-ran each test suite and spot-checked the load-bearing claims in the subagent's report by reading the diff and grepping the source — not just trusting "tests pass." At the end, both final repositories were stripped of every process artifact (state files, skill folders, instructions) and handed to a third, separate agent as anonymous X / Y folders, with the review rubric and per-stage metrics table but no knowledge of which was which.

What the blind reviewer found

A separate agent, shown only the anonymized final code and the rubric, ran both suites again itself and then went looking for ways to break each repository's stated invariants — not just reading whether tests were green.

Strongest evidence for Guide

  • Stage 4's single-enforcement-point claim is runtime-proven: the reviewer found a test that monkey-patches the shared guard to a no-op and asserts both start paths open, then patches it to always refuse and asserts both close — not string-matching, a real proof.
  • Backend equivalence is structural: a new storage backend is auto-enrolled into ~40 shared behavioral cases and two full CLI-transcript comparisons; forgetting to register one fails the suite by design.
  • One assignment concept with a kind tag makes "human or AI, never both" unrepresentable, rather than relying on two fields kept in sync by convention.

Strongest evidence for Direct

  • Consistently smaller, more literal changes per stage — stage 2 alone: +452/−16 across 7 files vs. Guide's +1044/−73 across 10, for the identical request.
  • Built almost exactly what was asked: an AI agent really is just (provider, model). Guide's agent registry, ids, display names, and execution history were all invented beyond the ask, and had to be carried through every later stage.
  • Better "clearly report why a task is blocked" — proactively shown in show, reusing one shared message function; Guide's equivalent prints bare hex ids with no explanation until you actually try the blocked action.

The real bugs neither self-report caught

These surfaced only when the blind reviewer constructed adversarial inputs — not from either subagent's own tests, and not from the orchestrator's lighter spot-checks:

"I loaded a record with both [a human assignee and an agent] set… the human silently disappears… Neither the invariant nor this case is tested in [Direct]."

"In [Direct], get_task returns the live object… a mutation persists… the stored state ends up self-contradictory" — a task can be saved as in progress while its own blocked_reason() still calls it blocked.

"Because [Direct]'s TaskService.__init__ loads the whole list once and _save() writes that same snapshot, a second session's work is silently destroyed" — demonstrated directly: one concurrent session's task vanishes from the file.

And the reviewer was equally willing to find Guide's protection accidental where it was accidental: "Neither repo defends invariant 8 against direct mutation. Guide happens to be safe in its shipping configuration; running Guide against an in-memory repository — exactly what Guide's own tests use — the bypass works identically."

Synthesis

What this says about the original question

Two things this pilot was set up to probe, weighed against what happened:

Was the deterministic layer a waste of time?

This pilot didn't run Balash's rule engine on either repository, so it can't speak to that engine directly. But it does bear on the deeper claim — that shaping the model's own objective can substitute for external verification. It doesn't support that reading. Guide's real advantage wasn't "trust the model's judgment more"; it was building verification that outlives the coding session — a test that would fail if someone later duplicated the enforcement rule, a suite that auto-enrolls a forgotten backend. That is a deterministic instinct, expressed as code the model wrote, not a reason to drop deterministic checking.

Was the earlier citation-hallucination problem a weak-model artifact?

Partially, and only partially. Across all four stages, light verification — rerun the suite, grep for one specific claimed structure — never caught a false statement from either strong-model subagent; that's consistent with your hypothesis. But the blind reviewer, working adversarially rather than confirmatively, found three real defects in Direct's code that this same light verification walked straight past: a violable core invariant, a persisted contradictory state, and a lost-update bug under concurrent sessions. Stronger models reduced the rate of the model simply lying about what it did. They did not reduce the rate of the model's own test suite having a blind spot — and that second failure mode is what an adversarial pass is for, independent of how strong the model writing the code was.

Limits

What this pilot doesn't establish

  • n = 1 per condition. The runbook's own bar for trustworthy evidence is three independent runs per condition with fresh contexts; this is the minimum pilot, not a conclusion.
  • The blind reviewer had final-snapshot code plus stage-level metrics, not full stage-by-stage trees — "did this stage need a preparatory refactor?" was inferred from diff size, not observed directly.
  • Both conditions used the same implementation model by design (a controlled variable), so this pilot doesn't yet test your two-strong-models split (a dedicated objective-setting model vs. a dedicated execution model) as a distinct condition.

Natural next steps

  • Replicate: two more independent runs per condition before treating any of this as a trend rather than an anecdote.
  • Reveal a fifth, still-hidden stage — the protocol's own prediction is that the gap should widen or narrow more clearly as change accumulates.
  • Point Balash's actual deterministic CLI at both final repositories, to see what it would have caught statically versus what only the blind adversarial pass found.
